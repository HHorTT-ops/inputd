# テストと受け入れ

[简体中文](testing.md) | [English](testing.en.md) | [日本語](testing.ja.md)

inputd は決定的自動テスト、明示的に有効化する Win32 注入テスト、実アプリ受け入れを分離します。合成入力の結果を、保護または管理者権限ゲームにおける物理 Raw Input 収録の証拠として扱ってはいけません。

## 自動テスト

既定の Release テスト：

```powershell
dotnet test InputExecutor.sln -c Release
```

既定テストは実ポインターや実キーを意図的に操作せず、次を検証します：

- 符号付き相対マウスとスキャンコード down/up；
- 複数キー／ボタンの held；
- Realtime 状態差分、latest-wins、deadline 期限切れ；
- 有界 Command FIFO と並行シーケンス非混在；
- 切断、リース、フォーカス喪失、対象終了、Disarm、終了時の解放；
- JSONL 連番、manifest、原子的完成、ホットキー除去；
- 元タイミング再生と固定レート変換；
- OBS bridge のパス、メッセージ、排出、partial 処理；
- HTTP／WebSocket 統合。

## 明示的に有効化する Windows 注入テスト

実際の Windows ポインターとキーを操作します。機密アプリを閉じ、緊急停止を準備し、使い捨てテストウィンドウだけで実行してください：

```powershell
$env:INPUTD_RUN_WIN32_TESTS='1'
dotnet test tests/InputExecutor.Tests -c Release --filter Category=WindowsIntegration
```

正負移動、スキャンコードエッジ、複数キー held、グローバルホットキー、診断記録、再生クリーンアップ、可能な場合のポインター復元を検証します。

## スケジューラと安全性の受け入れ

手動試験では次を確認します：

1. HTTP/WebSocket ハンドラーは入隊だけを行い、バックエンドを直接呼ばない。
2. Command は FIFO で、並行シーケンスが混在しない。
3. 最新の保留 Realtime 期待状態フレームだけを実行する。
4. 期限切れ `deadline` は入力を生成しない。
5. Realtime 切断で全 executor-held 入力を解放する。
6. 対象のフォーカス喪失で held を解放し、セッションを一時停止する。
7. 対象／クライアント終了、Disarm、緊急停止、サービス終了後に held が残らない。
8. 終了時はスケジューラ破棄前に best-effort `release_all` を行う。

## Raw Input 記録の受け入れ

本番記録は Windows Raw Input を使用し、グローバル低レベル Hook を導入しません。診断モードでは inputd タグ付きイベント検証のため一時 Hook を使えますが、Stop 後に必ず解除します。

物理入力手順：

1. 対象が管理者権限なら Dashboard も昇格する。
2. 正確な対象を固定して新規記録を開始する。
3. 少なくとも二つのキーを押下／解放し、ボタン、スクロール、正負方向の移動を行う。
4. 停止し、保留書き込みがゼロになるまで待つ。
5. `sequence` が 1 から始まり欠落がないことを確認する。
6. 最終 held keys/buttons が空であることを確認する。
7. manifest が complete で JSONL の SHA-256 と一致することを確認する。
8. 記録境界ホットキーだけが除かれ、同時の無関係入力が残ることを確認する。

高頻度試験ではマウスパケットを継続しながら Dashboard の応答を確認します。表示は集約可能ですが、永続 JSONL は完全な順序付きストリームを保持し、終了時 dropped/pending がゼロでなければなりません。

## 再生の受け入れ

Test Monitor または使い捨てオフラインアプリで：

1. 検証済み完全 JSONL を選ぶ。
2. 正確に固定した対象を前面に保つ。
3. 物理キー held、ボタンエッジ、ホイール、符号付き相対移動を確認する。
4. Stop ホットキーとフォーカス変更で各一回中断する。
5. どちらもキューを消去し全入力を解放することを確認する。
6. 完全再生後、出力イベント数と `dx/dy/wheel` 合計を比較する。

一部ゲームは相対 `SendInput` のカメラ操作を無視します。既定互換経路と任意 Interception を分けて試験し、バックエンドを記録してください。アンチチート回避には使用しません。

## 固定レート学習データの受け入れ

完全軌跡を 20、40、60 Hz と少なくとも一つの任意レートへ変換し、次を確認します：

- フレーム番号と時間窓が連続；
- `source_event_count` 合計が元イベント数と同じ；
- 空フレームでも held を継承；
- フレーム内の短い押下／解放エッジを保持；
- 符号付き `dx/dy/wheel` 合計が元と同じ；
- 元／出力 SHA-256 が manifest と一致；
- 明示的許可なしでは partial／欠落データを拒否。

## OBS の受け入れ

Lua と bridge 導入後、短時間と長時間の記録を行います：

1. `RECORDING_STARTED` がスクリプトを止めず bridge 収録を開始する。
2. 活動中データを現在ユーザーの spool に `*.partial` で書く。
3. `RECORDING_STOPPED` が排出、ハッシュ、最終映像横への原子的移動を行う。
4. 映像、`.input.jsonl`、manifest が同じ stem を使う。
5. OBS／bridge 中断時は partial を残すが complete にしない。
6. 大きな軌跡の排出とハッシュ中も OBS が応答する。

## 実ゲーム受け入れ

オフラインまたは明示的に許可された環境だけで行います。対象同一性、整合性レベル、バックエンド、表示モード、マウス設定、イベント／欠落数、dropped/pending、最終 held、manifest hash を記録します。

合格する記録にはゲームが前面の間の物理キーエッジと正負相対マウス値が含まれます。複数回の開始／停止と少なくとも一度の継続記録を行い、個人録画、スクリーンショット、アカウント識別子、マシン固有パスをコミットしないでください。
